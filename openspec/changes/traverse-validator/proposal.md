# Traverse Validator

## Summary

Add opt-in structural validation for transformed AST nodes during traversal, while always propagating slot-specific validators through traversal attributes.

The validator system distinguishes local validation from recursive validation. Local validation checks one descend step: the current node and its direct child slots. Recursive validation repeats that process through the returned node subtree.

## Motivation

Removing `erl_lint` from macro return validation requires a replacement that verifies transformed AST shape, not just broad roles such as `expression`, `pattern`, or `guard`.

Role-only validation is insufficient because parent nodes impose slot-specific constraints. For example, a `binary_generator` has a binary-generator pattern slot and a binary-generator body slot; those slots cannot be represented accurately by only `pattern` and `expression`.

Validation also cannot run blindly on every traversal step. Traversal can rebuild ancestors because a child changed, but that does not mean each ancestor was directly generated by the caller. Revalidating every rebuilt ancestor would be too expensive and would produce errors at the wrong abstraction level.

## Scope

This change covers:

- Propagating slot-specific validators through traversal attributes.
- Keeping validator propagation active even when automatic validation is disabled.
- Adding explicit local and recursive syntax validation APIs.
- Adding `validate => boolean` as an opt-in traversal validation switch, defaulting to disabled.
- Validating only nodes directly changed by a walker return.
- Preserving macro-specific error attribution for macro-triggered validation failures.

This change does not cover:

- Reintroducing `erl_lint` semantic checks.
- Checking variable binding, function existence, type compatibility, or record availability.
- Automatically validating every rebuilt ancestor when only a child changed.
- Automatically validating whole forms or modules when a smaller node is changed.

## Expected Behavior

When traversal descends into a node, the child receives attribute metadata describing the exact parent slot validator that applies to it.

When `validate => false` or the option is omitted, traversal does not automatically validate changed nodes. Callers can still read the propagated validator and perform their own validation.

When `validate => true`, traversal validates only nodes directly changed by the walker return. If a child change causes a parent to be rebuilt, the rebuilt parent is not automatically treated as directly changed.

Macro expansion uses the propagated validator to validate macro returns and wraps failures as `{invalid_macro_return, Detail}` with the current and origin macro context.
