# Uniform Macros Design

## Current Behavior

The current external macro flow is staged by imported module:

```text
M1 attribute pass
M1 function pass
M2 attribute pass
M2 function pass
...
```

This means macro expansion depends on import order. A macro generated by `M2` that calls `M1` will not be expanded after the `M1` pass has already completed.

Within a single `MacroMap`, the existing traversal behavior is correct:

```text
pre traversal:  order = outer
post traversal: order = inner
```

The fix should target the macro environment boundary, not the `outer` / `inner` traversal logic.

## Proposed Flow

```text
1. Collect external macros and build ExternalUniformMap.

2. Expand external attribute macros globally.
   - Use ExternalUniformMap.
   - Expand attribute macros only.
   - Do not expand function body macros.

3. Discover local macro definitions and related functions from the updated forms.

4. Build the local macro source snapshot.
   - Expand only the local macro functions and related functions.
   - Use ExternalUniformMap only.
   - Do not use LocalMacroMap.
   - Do not expand local macros inside local macro definitions.

5. Compile and load the local macro module.

6. Build FinalUniformMap = ExternalUniformMap + LocalMacroMap.

7. Run final global form expansion.
   - Use FinalUniformMap.
   - Expand attribute macros.
   - Expand function body macros.
   - Preserve existing outer then inner traversal semantics.
   - Skip local macro functions and related functions.
```

## Uniform Macro Map

The uniform macro map must support both local-style and remote-style macro calls:

```erlang
{Function, Arity}
{{Module, Function}, Arity}
```

Remote calls must be matched by the remote module in the AST, not by a single module argument passed to the transform function.

## Local Macro Boundary

Local macro functions and related functions are a locked source snapshot for the temporary local macro module. They may be externally expanded before compilation, but they must not be modified by the final macro environment.

The final expansion phase must skip these functions to avoid changing behavior after the local macro module has already been compiled and loaded.

## Expansion Depth

`max_depth` is the maximum macro expansion chain depth. It limits a chain that starts from a macro call and continues through macro calls generated by expansion results.

This applies to same-macro recursion and cross-macro recursion alike:

```text
A -> A -> A
A -> B -> A
A -> B -> C
```

The default remains `100`. Call-site module options such as:

```erlang
-macro_options([{max_depth, 10}]).
```

can reduce the global chain limit for tests or stricter compilation. Definition-level macro options may still override the global value for a specific macro.

`max_depth` is not a total expansion count for the whole module. A module may contain many independent macro calls without consuming one shared global budget.

## Conflict Rules

Remote macro calls are exact:

```erlang
macro_mod:foo(X)
```

must resolve only to `macro_mod:foo/1`.

Unqualified calls may resolve through aliases or local macro entries. Local macro aliases should take precedence over external aliases when both define the same unqualified `{Function, Arity}` key.

## Open Questions

- Should attribute macro expansion become fixed-point if an attribute macro generates another attribute macro?
- Should dynamic external macro imports introduced by attribute macros be rejected in this phase or handled by a later module-level discovery fixed point?
